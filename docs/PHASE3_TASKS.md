# Phase 3 (Milestone M3) — Correlation, decision and report

**Window:** T+10h → T+14h. **Base:** `contract-1.0.2` (`d8ca3ee`). **Team:** Lead + PM (AI 1) build; AI 3 reviews.
**Goal (ARCHITECTURE.md §4–§5, §7 "Core diagnosis working"):** turn the agents' findings into **one defensible JSON diagnosis**: rank global fault signatures, weigh `supports` against `contradicts`, verify the leader with a QUERY (and the rival when close), apply the `heuristic-v1` confidence and the decision gates, abstain when evidence is thin, and publish a report whose every cited ID exists.

## Design decisions (Lead)
- **Correlation evaluates the signatures itself.** Agents nominate hypotheses (FINDINGs); Correlation checks each candidate's `required` / `corroborating` / `contradicting` checks from `signatures-1.0.yaml` against the canonical evidence, with the frozen check vocabulary and scopes. Agent count never adds confidence; a measurement counts once.
- **`heuristic-v1`** exactly as ARCHITECTURE §4: `raw = clamp(0.40·signal_fit + 0.25·topology_fit + 0.20·time_fit + 0.15·independent_source_fit − 0.15·contradiction_strength)`, `confidence = round(raw · coverage, 2)`. Factor definitions are documented in `netcoop/agents/correlation.py` and PROTOCOL.md.
- **QUERY rounds (≤ 2):** round 1 always verifies the leading cause's key measurement with its owning agent; round 2 queries the rival when it is within 0.15. The RESPONSE's evidence sets the hypothesis's *severity* (critical vs only warn), which can change the ranking. Before/after rankings go into the DECISION.
- **Gates:** diagnosed = conf ≥ 0.70, coverage ≥ 0.75, ≥ 2 independent raw sources, lead ≥ 0.15; probable = conf ≥ 0.50 with a named rival or limitation; healthy = no candidate passes its required checks **and** fresh normal performance + infrastructure measurements **and** passing service and path checks; otherwise insufficient_evidence.
- **Affected IDs:** a link target → `affected_segments: [link]`, `affected_devices: [device it feeds]`; a device target → `affected_devices: [device]`.

## Acceptance criteria (what AI 3 will check)
1. `heuristic-v1` computed exactly (unit test with hand-worked factors); the four gates enforced (one test per gate, including the lead and independent-source rules).
2. QUERY: every incident whose leading hypothesis has a key measurement owned by an in-process agent (congestion, interface fault, weak Wi-Fi, device overload, hardware failure) sends ≥ 1 QUERY and gets a RESPONSE through the bus (DNS/DHCP: the service checks are Connectivity's own pass/fail evidence, already in hand, with no severity level to verify, so no QUERY); never more than 2 rounds; on `ambiguous_congestion_errors` the QUERY changes the ranking, recorded in the DECISION.
3. Report: every field present; `confidence_method: heuristic-v1` with a computed value (no placeholder, C2); a `diagnosed` report's `supporting_evidence` comes from ≥ 2 distinct raw sources (C1); every cited evidence / finding ID exists; every affected ID is in the topology; `alternative_causes`, `recommended_actions` and `limitations` filled; a Markdown report is written next to the JSON.
4. Robustness: `netcoop/0.9` upgraded with a visible conversion record (C8); 2.x → `SCHEMA_VERSION_UNSUPPORTED`; a FINDING citing unknown evidence → `UNKNOWN_EVIDENCE` and excluded; Correlation timeout → one retry → `insufficient_evidence` + `correlation_failed` + `AGENT_TIMEOUT` (C8); non-UTC offsets converted and logged (C5); the per-record quarantine decision (C4) documented.
5. Accuracy on the 17 labelled dev scenarios (`scenarios/labels.json`, never read at runtime): status, cause and affected IDs reported per scenario, with any miss explained, not hidden.
6. Deterministic; `pytest -q` green; schemas unchanged (no contract change needed).

## Decisions recorded during the phase
- **C4 (per-record quarantine) — decided: keep whole-incident `invalid_input`.** One unknown metric or unknown device means the source and our mapping disagree; diagnosing the rest would silently drop evidence an operator expects to be used. The report lists every field-level error so the input can be fixed and re-run. Revisit only if held-out evaluation (Phase 4) shows real inputs mixing good and bad records.
- **Fixture/answer-key corrections after the first Phase 3 run (13/17 → 17/17), stated openly:** (1) reachability now comes from an `icmp-monitor` source instead of the `client-probe` that also runs DNS/DHCP checks (in a real campus the ping poller and synthetic DNS probes are separate tools; with one shared source the two-source gate made every service fault `probable`); (2) `labels.json` 1.1 adds the fed device to the affected IDs of `ambiguous_congestion_errors` and `schema_0_9`, matching the other four link-fault labels and the affected-ID rule fixed above before the run. No threshold, weight or gate was changed to fit a label.

## Phase 3 review (AI 3: REJECTED narrow, feedback3.md) — what changed
No threshold value, weight or gate value moved. Every change is decision logic, an explicit semantic, or evidence handling:
- **R1 — refuted vs unresolved.** A candidate is *refuted* when a required check fails or a contradicting check passes. It is *unresolved* when it is not refuted but is unassessed (a required check has no usable evidence and coverage < 0.75) or a required check is *inconclusive*. An unresolved candidate raised by an agent blocks `diagnosed`, is listed in `alternative_causes` with a limitation saying why ("could not be assessed: … 2 of 3 required fresh samples" / "is inconclusive: …") and gets a recommended action to collect the evidence. `alternative_causes` = every nominated candidate except refuted ones.
- **Check states:** `pass` / `fail` / `unknown` (no usable evidence) / **`inconclusive`** (evidence present but undecided). `sustained_above_critical`: a run ends only at a sample at or below warn or a missing interval (a dip into the warn band is hysteresis, written into the YAML vocabulary); with no run it *fails* only if the link is not even elevated (fewer than N samples above warn), otherwise it is *inconclusive*. Inconclusive counts as assessed for coverage, earns half credit in `signal_fit`, and can never be diagnosed.
- **Ties** at the reported 2-decimal precision are broken by `signal_fit` (stronger signature evidence), then name — previously by name alone; the tie is written to the DECISION.
- **R2 — utilization cross-check.** Disagreement beyond `utilization_cross_check.tolerance_points` (YAML, 5) is logged and the measured value kept; it is `malformed` only when the two disagree about the verdict (one above critical, the other at or below warn). A throughput/capacity ratio above `max_throughput_ratio_pct` (110) skips the cross-check. The derived estimate is now **kept alongside** the measured one (flag `derived`, same `source_id`, so independence is not inflated); each estimator's series is judged on its own.
- **R3 — noise gate** `tests/test_noise_robustness.py`: AI 3's noise function (also applied to probe samples), 10 core scenarios × seeds 1–10 × σ 0.05/0.10. Result: σ 0.05 → 100/100 exact; σ 0.10 → 93 exact, 6 probable-instead-of-diagnosed (same cause), **0 false faults, 0 wrong `diagnosed`**, 1 hedged wrong cause (ambiguous seed 7: `probable interface_fault`, congestion listed as alternative and "inconclusive, not ruled out" — its utilization never forms a sustained run above critical; naming congestion would need tuning to that seed).
- **R4 — QUERY honesty.** Scenarios can carry `on_query` probe samples (`source_id: on-demand-probe`), released only when a QUERY asks; the RESPONSE then cites new evidence IDs and severity is graded from them (counter rates scaled to the YAML's per-minute interval). Without probe data the RESPONSE and DECISION say "no new probe was run".
- Deferred (P2, non-blocking): P2-1 per-interval deltas next to cumulative counters in the report; P2-2 scoping the healthy gate's missing/stale rule to the area in question; P2-3 one-source DNS/reachability cases in the Phase 4 held-out set; P2-4 kept (README documents the timeout confidence string).
